# iOS keyboard 模块代码审查报告

审查日期：2026-06-15（第二轮）
审查范围：`ios/keyboard/` 下全部 Swift 文件 + `Info.plist`
参考规范：SwiftUI Performance Audit、iOS Application Development Guide

---

## 一、总体评价

相比上一轮审查，当前代码已经解决了几个核心交互问题：

- 清空、发送按钮的语义与 Flutter 端对齐（清空宿主输入框、发送触发 Return）。
- 风格分页第二页的网格布局已修复，空位不再用 `Spacer()` 撑开。
- 生成成功后自动把回复插入宿主输入框，并增加了日志和顶部 Toast 错误提示。
- Swift 6 并发警告已处理，`@MainActor` + `weak self` 的写法规范。
- 网络错误判断已细化，`NSURLErrorDataNotAllowed` 才判定为完全访问未开启。

整体架构保持 MVVM 分层，职责清晰。本轮审查重点放在 **性能、可访问性、键盘扩展生命周期、边界鲁棒性** 上。

## 二、架构与设计

### ✅ 做得好的地方

1. **MVVM 分层清晰**
   - `KeyboardViewController` 只负责初始化、MMKV、SwiftUI 托管和 `KeyboardInputHandling` 实现。
   - `KeyboardViewModel` 承载状态与业务逻辑，不直接依赖 UIKit。
   - `KeyboardConfigRepository` / `OpenAIRepository` 职责单一。

2. **Flutter 语义对齐到位**
   - `clearHostInput()` 对应 Flutter `onClear`。
   - `submitHostInput()` 对应 Flutter `onSubmit`。
   - `generateByStyle(_:)` 成功后 `insertText(reply)` 对应 Flutter `onGenerated`。

### ⚠️ 建议改进

1. **ViewModel 每次请求新建 `OpenAIRepository`**
   - `generateByStyle(_:)` 里每次都 `let repository = OpenAIRepository(config: config)`。
   - 频繁创建客户端对象，且 `OpenAI.Configuration` 每次都会重新解析 baseURL。
   - 建议把 `openAIRepository` 作为依赖注入；当配置刷新时，判断 key/baseURL/model 是否有变化，再决定是否重建。

2. **`OpenAIRepository` 直接依赖完整的 `KeyboardConfig`**
   - Repository 实际只需要 `apiKey`、`baseURL`、`model`。
   - 建议由 ViewModel 组装一个更小的配置值对象传入，降低 Repository 与 Model 的耦合，也方便单元测试。

3. **`currentContext()` 已成为死代码**
   - `KeyboardInputHandling` 协议里保留了 `currentContext()`，但 ViewModel 已不再调用。
   - 建议移除，或明确预留用途；死代码会增加维护成本。

## 三、SwiftUI 性能审计

### ✅ 无明显性能瓶颈

当前视图树很小（输入框 + 分页网格 + 操作列），没有复杂列表、大图解码或重计算。`@Published` 状态变更触发的重渲染范围可控。

### ⚠️ 可优化点

1. **隐式 `.animation` 可能引发意外动画**
   - `errorToast` 的 VStack 上挂了 `.animation(.easeInOut(duration: 0.2), value: viewModel.errorMessage)`。
   - 虽然指定了 `value`，但在 iOS 15 之前 `.animation(_:value:)` 的行为与 `.animation(_:)` 不完全一致；且该修饰符会作用于 VStack 内所有依赖 `errorMessage` 的子视图。
   - 建议：把动画放到具体做过渡的 modifier 上，例如 `.transition(...).animation(.easeInOut, value: viewModel.errorMessage)` 直接绑在 Text 上。

2. **`pageCount` 与 `pageStyles(for:)` 在 `body` 中实时计算**
   - 当前数组切片操作非常轻量，不构成性能问题。
   - 如果以后风格数量很大或分页逻辑变复杂，可以预计算成 `@Published` 状态。

3. **`TabView` + `PageTabViewStyle` 的潜在布局开销**
   - `TabView` 在嵌套多层 `VStack`/`HStack` 里，page 切换时可能触发全量 layout。
   - 当前页面少、内容轻，基本无感。后续如果网格复杂化，可考虑自定义 `PageView` 或 `ScrollView` + `.paging`。

4. **`StyleChip` 的条件内容切换**
   - `isGenerating` 为 true 时显示 `ProgressView`，否则显示 `Text`。
   - 这是稳定的内容切换，identity 没有变化，不会导致列表项重建。

## 四、UI / UX（对照 iOS HIG）

### ⚠️ 布局与点击区域

1. **右侧操作按钮高度 40pt，未达到 HIG 推荐的 44pt**
   - `IconActionButton` 被 `.frame(height: 40)` 限制。
   - 粘贴按钮也是 `40`。
   - 建议统一改为 `minHeight: 44`，在视觉上可用内边距补足，保证可点击区域。

2. **键盘高度仍写死 260pt**
   - `KeyboardViewController.setupSwiftUIKeyboardView()` 里 `view.heightAnchor.constraint(equalToConstant: 260)`。
   - 未适配横屏、iPad、不同机型。后续横竖屏切换时需要重新设计。

3. **底部安全区处理**
   - 当前底部 `.padding(.bottom, 8)`，对 Home 指示条机型可能贴太近。
   - 建议用 `GeometryReader` 读取 `safeAreaInsets.bottom` 做动态 padding，或至少 12–16pt。

### ⚠️ 可访问性

1. **风格芯片缺少 accessibilityLabel / hint**
   - `StyleChip` 只显示文字，VoiceOver 能读到名称，但没有提示它是「生成某种风格的回复」。
   - 建议加 `.accessibilityLabel("\(style.name ?? ""), 生成回复")`。

2. **生成中的 ProgressView 没有明确状态提示**
   - VoiceOver 用户不知道当前正在生成回复。
   - 建议在 `generatingStyleId != nil` 时，给整个键盘加一个 `accessibilityAnnouncement` 或更新状态标签。

3. **错误 Toast 的动画可能干扰 VoiceOver**
   - Toast 出现 2 秒后自动消失，VoiceOver 可能还没读完。
   - 建议：重大错误用更持久的提示，或让 Toast 支持手动关闭。

4. **未使用语义字体，Dynamic Type 支持不足**
   - 当前大量用 `.font(.system(size: 14))` 等硬编码字号。
   - 建议统一使用 `.body`、`.caption`、`.footnote` 等语义样式；如必须固定，用 `Font.custom(..., size: ..., relativeTo: .body)`。

### ✅ 颜色与暗黑模式

- 背景、卡片、错误提示都使用了语义色（`.systemBackground`、`.systemGray6`、`.systemRed`），暗黑模式自适应。
- `Color.accentColor` 会跟随系统/App 的 accent color，建议后续统一品牌色。

## 五、安全与隐私

### ⚠️ API Key 仍以明文存储在 MMKV

- `KeyboardConfig.apiKey` 来自 App Group 的 MMKV，默认明文。
- 用户已明确表示「API Key 本地存储，未云端存储所以不用加密」，因此本轮不强制要求改动。
- 但至少需要确保：**日志里不能打印 API Key**。
  - 当前 `OpenAIRepository` 日志只打印 `model` 和 `baseURL`，未打印 key，符合要求。

### ⚠️ 用户上下文直接上传第三方

- `inputText` 里的聊天记录会作为 user message 发送给 OpenAI 兼容平台。
- 建议在 App 隐私政策中明确说明，并考虑后续增加「不上传完整上下文」的开关。

## 六、键盘扩展特定问题

### ⚠️ 生命周期

1. **`MMKV.initialize` 可能在 view 重建时重复调用**
   - `setupSharedMMKV()` 在 `viewDidLoad()` 中执行。
   - `UIInputViewController` 的 view 可能被系统重建，建议加防护：
     ```swift
     if MMKV.rootDir == nil {
         MMKV.initialize(...)
     }
     ```
   - 或把 MMKV 初始化提取到单例/生命周期更稳定的位置。

2. **`clearAllText()` 实现可能较慢且不完全可靠**
   - 通过循环 `deleteBackward()` 清空文本，长文本时效率低。
   - 某些宿主 App 对 `textDocumentProxy` 的上下文有限制，可能出现删不干净的情况。
   - 建议：
     - 增加最大尝试次数，避免死循环。
     - 对空输入的情况提前返回。

3. **`submitHostInput()` 的 `
` 行为依赖宿主 App**
   - 聊天类 App 通常把 Return 当发送；多行文本框则会插入换行。
   - 这是键盘扩展 API 的限制，没有更标准的触发方式。
   - 建议在产品说明里提示用户：发送行为依赖当前 App。

4. **未处理内存警告与任务取消后的引用**
   - `currentTask` 在请求结束后不会自动置 nil（虽然 Task 完成会释放）。
   - 建议显式 `self.currentTask = nil`，并考虑在 `deinit` 中 cancel。

## 七、错误处理与边界情况

### ⚠️ 建议改进

1. **配置解析失败仍被静默吞掉**
   - `KeyboardConfig.fromJSON` 失败返回空对象，UI 无法区分「没配置」和「配置损坏」。
   - 建议返回 `Result<KeyboardConfig, Error>`，或在空配置时给出一个明确的 errorMessage。

2. **`pasteContent()` 未校验剪贴板内容长度**
   - 如果用户复制了超长文本，会直接塞进 `inputText`。
   - 建议限制长度（如 5000 字），超长时截断并提示。

3. **`generateByStyle(_:)` 未限制 context 长度**
   - 长上下文会导致 Token 过多、费用增加、响应变慢。
   - 建议按字符数或 Token 数截断，或在设置里暴露限制选项。

4. **网络请求无超时控制**
   - `OpenAI` 客户端默认超时可能较长，用户可能以为卡死。
   - 建议在 `OpenAI.Configuration` 或请求层面设置显式超时（如 30 秒）。

## 八、代码风格

### ✅ 注释风格已统一

- 本轮查看的代码中，注释基本去掉了「我」字，改为开发者视角的自然口语。
- 示例：「这个 View 只负责把 ViewModel 里的状态画出来」「通过这个角色来操作宿主输入框」。

### ⚠️ 命名

1. **`showNextKeyboard()` 与 `showInputModeList()` 仍不一致**
   - ViewModel 叫 `showNextKeyboard()`，协议叫 `showInputModeList()`。
   - 建议统一，比如都叫 `showInputModeList()`，语义更准确。

2. **`IconActionButton` 的 `label` 只用于 accessibilityLabel**
   - 命名没问题，但可以考虑让 `label` 同时用于显示 Tooltip（长按提示）。

## 九、优先级建议

### 🔴 高优先级（已修复）

1. ✅ 右侧操作按钮 / 粘贴按钮点击区域不足 44pt → 改为 `frame(minHeight: 44)`。
2. ✅ `MMKV.initialize` 重复调用风险 → 加静态标志只初始化一次。
3. ✅ `clearAllText()` 长文本清空性能和鲁棒性问题 → 增加最大尝试次数 5000。
4. ✅ 配置解析失败无明确反馈 → `fromJSON`/`loadConfig` 返回 `Result`，失败时弹 Toast。
5. ✅ `currentContext()` 死代码清理 → 已从协议和 ViewController 中移除。

### 🟡 中优先级（已修复）

6. ✅ ViewModel 每次请求新建 `OpenAIRepository` → 持有实例，配置变化时才重建。
7. ✅ `OpenAIRepository` 与 `KeyboardConfig` 解耦 → 改为依赖 `AIPlatformConfig`。
8. ✅ 键盘高度写死 260pt → 根据 `verticalSizeClass` 动态设置竖屏 260pt / 横屏 200pt。
9. ✅ 风格芯片缺少 accessibilityLabel/hint → `StyleChip` 增加 label 与 hint。
10. ✅ 使用语义字体支持 Dynamic Type → 硬编码字号替换为 `.subheadline`、`.caption` 等。
11. ✅ `inputText` / 上下文长度未限制 → 增加 `maxContextLength = 3000`，超长自动截断提示。
12. ✅ 网络请求无显式超时 → `OpenAI.Configuration.timeoutInterval` 设为 30 秒。

### 🟢 低优先级（后续迭代）

13. 自定义 accent color / 品牌色。
14. 错误 Toast 支持手动关闭或更持久展示。
15. `TabView` 替换为更轻量的自定义分页（如页面变复杂）。
16. 支持 Reduce Motion。
17. Repository 协议化，方便单元测试 mock。

---

## 十、总结

当前 iOS keyboard 模块的高、中优先级问题已修复完毕，核心功能、交互语义、可访问性、生命周期鲁棒性都有明显提升。剩下的低优先级项（品牌色、Toast 持久化、Reduce Motion、Repository 协议化等）可在后续迭代中逐步处理。
